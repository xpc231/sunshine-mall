# Idempotent模块设计说明

## 设计原则：YAGNI（You Aren't Gonna Need It）

### 为什么采用简洁设计？

本模块遵循YAGNI原则，只实现核心必需功能，避免过度设计。

## 设计决策

### 1. 为什么使用Redis作为唯一存储？

实际需求分析：
- Redis的SETNX天然支持幂等性控制
- 分布式环境下性能优异
- 自动过期机制完美匹配幂等场景
- 项目已集成Cache模块，零额外依赖

不需要的抽象：
- 不支持数据库存储（性能差，不适合高并发）
- 不支持ZooKeeper（过于重量级）
- 不提供存储策略接口（只有一种实现，无需抽象）

### 2. 为什么使用AOP切面？

优势：
- 声明式编程，业务代码无侵入
- 统一处理，避免重复代码
- 易于维护和扩展

实现方式：
- @Around环绕通知拦截方法执行
- 前置检查幂等性
- 后置处理异常情况

### 3. 为什么使用SpEL表达式？

灵活性：
- 支持参数引用：#orderId
- 支持对象属性：#order.orderId
- 支持表达式组合：#userId + ':' + #articleId
- 支持固定字符串：'fixed-key'

已足够满足需求，无需自定义复杂的键生成器。

### 4. 为什么不支持多种存储策略？

当前只需要Redis：
- Redis性能和功能完全满足需求
- 避免接口抽象的复杂性
- 如果未来需要，重构成本很低

### 5. 为什么业务异常时删除幂等键？

允许用户重试：
- 网络抖动、超时等临时性问题
- 业务逻辑异常（如库存不足）
- 提升用户体验，不会"卡死"请求

## 核心组件

### 1. @Idempotent注解

职责：标记需要幂等控制的方法

设计：
- key：SpEL表达式，灵活定义幂等键
- prefix：区分不同业务场景
- expireTime：自动过期，避免永久占用
- message：自定义错误提示

### 2. IdempotentAspect切面

职责：拦截@Idempotent注解的方法，执行幂等检查

核心逻辑：
```
1. 解析SpEL表达式生成幂等键
2. 使用CacheManager.setIfAbsent尝试设置（SETNX）
3. 设置成功 → 执行业务方法
4. 设置失败 → 抛出IdempotentException
5. 业务异常 → 删除幂等键，允许重试
```

### 3. IdempotentException异常

职责：标识重复提交异常

设计：
- 继承RuntimeException
- 携带自定义错误消息
- 由全局异常处理器统一处理

### 4. IdempotentConfig配置类

职责：启用AOP和组件扫描

设计：
- @EnableAspectJAutoProxy启用AOP
- @ComponentScan扫描幂等组件
- 通过spring.factories实现自动配置

## 复用现有组件

### 1. CacheManager（cache模块）

用途：Redis操作

复用的功能：
- setIfAbsent：实现SETNX，核心幂等逻辑
- delete：删除幂等键
- hasKey：检查幂等键是否存在（测试用）

为什么不直接使用RedisTemplate？
- CacheManager提供了统一的异常处理
- 简化了key的序列化逻辑
- 保持框架内部的一致性

### 2. Spring AOP

用途：方法拦截

依赖：spring-boot-starter-aop

### 3. Spring SpEL

用途：动态表达式解析

使用场景：
- 从方法参数提取幂等键
- 支持复杂表达式组合

## 工作流程

### 正常流程

```
用户请求
    ↓
AOP拦截
    ↓
解析SpEL表达式 → 生成幂等键（prefix:key）
    ↓
Redis SETNX幂等键
    ↓
成功？
├─ 是 → 执行业务方法 → 返回结果
└─ 否 → 抛出IdempotentException
```

### 异常处理流程

```
业务方法执行
    ↓
抛出异常
    ↓
删除幂等键（允许重试）
    ↓
向上抛出原始异常
```

## 幂等键设计

### 格式

```
{prefix}:{key值}
```

### 示例

```
默认：idempotent:order-123
自定义前缀：pay:order-123:999.00
多参数：inventory:deduct:product-1:user-100
```

### 设计原则

1. 唯一性：能唯一标识一次业务操作
2. 简洁性：避免过长，节省内存
3. 可读性：便于调试和监控
4. 一致性：同一业务使用统一格式

## 性能设计

### 1. 轻量级实现

避免重量级操作：
- 不使用数据库存储
- 不使用分布式锁（性能开销大）
- 基于Redis SETNX，原子操作

### 2. 自动过期

避免内存泄漏：
- 默认60秒过期
- 支持自定义过期时间
- Redis自动清理，无需手动管理

### 3. 异常快速失败

检测到重复提交：
- 立即抛出异常，不占用资源
- 不等待、不重试
- 快速响应客户端

## 与其他方案对比

### 1. vs 分布式锁

| 特性 | 幂等性 | 分布式锁 |
|------|--------|----------|
| 目的 | 防止重复提交 | 保证互斥访问 |
| 使用场景 | 同一请求多次提交 | 多个请求并发竞争 |
| 失败行为 | 直接拒绝 | 等待或快速失败 |
| 复杂度 | 简单 | 复杂（需要锁续期、释放） |
| 性能 | 高 | 中等 |

### 2. vs 数据库唯一索引

| 特性 | Redis幂等 | 数据库唯一索引 |
|------|-----------|----------------|
| 性能 | 极高 | 中等 |
| 灵活性 | 高（支持过期） | 低（永久有效） |
| 适用场景 | 高并发、临时幂等 | 低并发、永久唯一 |
| 维护成本 | 低 | 低 |

### 3. vs Token机制

| 特性 | 自动幂等 | Token机制 |
|------|----------|-----------|
| 使用方式 | 注解声明 | 手动获取Token |
| 代码侵入 | 无 | 有 |
| 适用场景 | 后端API | 前端表单 |
| 复杂度 | 简单 | 中等 |

## 总结

遵循YAGNI原则，当前实现：
- 核心功能完整：基于Redis的幂等控制
- 使用简单：声明式注解 + SpEL表达式
- 性能优异：轻量级实现，高并发支持
- 易于扩展：模块化设计，低耦合

当前功能已满足大部分业务场景。复杂功能待真正需要时再实现。
